# คู่มือการใช้งานระบบแอดมิน Calories Guard

คู่มือนี้สำหรับผู้ดูแลระบบที่ใช้ Admin Web เพื่อจัดการข้อมูลอาหาร ตรวจคำขอจากผู้ใช้ และดูข้อมูลผู้ใช้

## 1. URL และสิทธิ์การเข้าใช้งาน

URL production:

`https://admin.caloriesguard.com`

เงื่อนไขการเข้าใช้งาน:

- ต้องมีบัญชีผู้ใช้ในระบบ
- `users.role_id` ต้องเป็น `1`
- backend จะตรวจสิทธิ์ผ่าน `get_current_admin`

ถ้า login ได้แต่ถูกเด้งกลับหน้า login หรือเจอ 403 แปลว่าบัญชีนั้นยังไม่ใช่ admin

## 1.1 บทบาทของแอดมิน

แอดมินรับผิดชอบข้อมูลที่มีผลกับผู้ใช้ทั้งระบบ ได้แก่:

- ตรวจความถูกต้องของฐานข้อมูลอาหาร
- เพิ่ม/แก้ไข/ลบรายการอาหาร
- ตรวจคำขออาหารใหม่จากผู้ใช้
- ตรวจชื่ออาหารท้องถิ่น
- ดูรายการผู้ใช้เพื่อ support และตรวจสิทธิ์

สิ่งที่แอดมินไม่ควรทำ:

- แก้ข้อมูลอาหารโดยไม่มีแหล่งอ้างอิง
- ลบอาหารจำนวนมากโดยไม่ตรวจผลกระทบ
- เปิดเผยข้อมูลผู้ใช้ให้บุคคลภายนอก
- ใช้บัญชี admin ร่วมกันหลายคน

## 2. เข้าสู่ระบบ

1. เปิด Admin Web
2. กรอกอีเมลและรหัสผ่าน
3. กดเข้าสู่ระบบ
4. ระบบจะเก็บ token ใน browser localStorage ภายใต้ key `cg_admin_auth`

Token มีอายุประมาณ 12 ชั่วโมง หลังจากหมดอายุให้ login ใหม่

หลังเข้าสู่ระบบ ระบบจะตรวจ `role_id`:

- `role_id = 1`: เข้า admin ได้
- ค่าอื่น: ถูก redirect หรือได้รับ 403

ถ้าต้อง debug ให้เปิด browser DevTools -> Network แล้วดูว่า request มี header `Authorization: Bearer <token>` หรือไม่

## 3. Dashboard

หน้า Dashboard แสดงภาพรวมของระบบ เช่น

- จำนวนอาหารในระบบ
- จำนวน Temp Foods ที่รออนุมัติ
- จำนวนคำเสนอชื่ออาหารท้องถิ่นที่รอตรวจ
- รายการ Temp Foods ล่าสุด

ใช้หน้านี้เพื่อดูงานที่ต้องตรวจประจำวัน

งานประจำวันแนะนำ:

1. ดูจำนวนคำขอรอดำเนินการ
2. ตรวจ Temp Foods ที่ส่งเข้ามาใหม่
3. ตรวจชื่ออาหารท้องถิ่น pending
4. ตรวจรายการอาหารหลักที่ถูกแก้ไขล่าสุด ถ้ามี workflow ภายนอกแจ้งมา
5. ทดสอบค้นหาอาหารยอดนิยมเพื่อดูว่าข้อมูลยังแสดงถูกต้อง

## 4. จัดการอาหาร

เข้าเมนู `Foods`

สิ่งที่ทำได้:

- ดูรายการอาหารทั้งหมด
- ค้นหาอาหาร
- เพิ่มอาหารใหม่
- แก้ไขข้อมูลอาหาร
- อัปโหลดรูปอาหาร
- ลบอาหาร

ข้อมูลอาหารที่ควรกรอก:

- ชื่ออาหาร
- แคลอรี่
- โปรตีน
- คาร์บ
- ไขมัน
- รูปภาพ
- หมวดหมู่หรือชนิดอาหาร ถ้ามี
- โซเดียม น้ำตาล คอเลสเตอรอล ไฟเบอร์ ถ้ามีข้อมูล

ข้อควรระวัง:

- การแก้ไขอาหารมีผลกับรายการใหม่ที่ผู้ใช้บันทึกหลังจากแก้
- ควรตรวจหน่วยเสิร์ฟและค่า kcal ให้ถูกต้องก่อนบันทึก
- หลีกเลี่ยงการลบอาหารที่ผู้ใช้อาจอ้างอิงอยู่ ควรแก้ข้อมูลแทนถ้าเป็นไปได้

### 4.1 เกณฑ์คุณภาพข้อมูลอาหาร

ก่อนบันทึกหรือแก้ไข ให้ตรวจ:

- ชื่ออาหารสะกดถูกต้องและไม่กำกวม
- ค่า kcal สอดคล้องกับปริมาณต่อ serving
- โปรตีน คาร์บ ไขมัน ไม่เป็นค่าติดลบ
- ถ้ามีรูป ควรเป็นรูปอาหารจริง ไม่ใช่รูปไม่เกี่ยวข้อง
- ไม่สร้าง duplicate ถ้ามีเมนูเดียวกันอยู่แล้ว
- ถ้าเป็นอาหารท้องถิ่น ให้แยกระหว่างชื่อ canonical กับ regional alias ให้ชัด

### 4.2 วิธีเพิ่มอาหารใหม่

1. เข้าเมนู `Foods`
2. กด `เพิ่มเมนูใหม่`
3. กรอกชื่ออาหาร
4. กรอก kcal, protein, carbs, fat
5. ใส่ URL รูปภาพหรืออัปโหลดรูป
6. ตรวจ preview รูป
7. กด `เพิ่มเมนู`
8. ค้นหาอาหารนั้นอีกครั้งเพื่อยืนยันว่าเพิ่มสำเร็จ

### 4.3 วิธีแก้ไขอาหาร

1. ค้นหาอาหารใน `Foods`
2. กดไอคอนแก้ไข
3. ปรับข้อมูลที่ต้องการ
4. กดบันทึก
5. refresh หน้า และตรวจค่าที่แสดง

### 4.4 วิธีลบอาหาร

1. ค้นหาอาหาร
2. กดไอคอนลบ
3. อ่าน confirmation
4. ยืนยันเฉพาะเมื่อมั่นใจว่าไม่ควรอยู่ในระบบ

คำแนะนำ: ใน production ควรใช้การ soft delete หรือแก้ข้อมูลแทนการลบถาวร ถ้า backend รองรับ

## 5. ตรวจ Temp Foods

เข้าเมนู `Food Requests`

Temp Foods คือรายการอาหารที่ผู้ใช้เพิ่มเองหรือ AI ช่วยประเมิน แล้วรอ admin ตรวจสอบ

### 5.1 อนุมัติอาหาร

1. เปิดรายการที่รอตรวจ
2. กดอนุมัติ
3. ตรวจชื่ออาหารและข้อมูลโภชนาการ
4. เช็กรายการอาหารใกล้เคียงเพื่อป้องกัน duplicate
5. ปรับข้อมูลหากจำเป็น
6. อัปโหลดรูปภาพถ้ามี
7. กดยืนยัน

เมื่ออนุมัติแล้ว backend จะเพิ่มรายการเข้าสู่ catalog หลัก และ mark รายการ temp ว่าตรวจแล้ว

ข้อมูลที่ควรตรวจก่อนอนุมัติ:

- ชื่อเมนูเหมาะสม
- ไม่ซ้ำกับเมนูเดิม
- kcal อยู่ในช่วงสมเหตุสมผล
- macro รวมไม่ขัดแย้งอย่างรุนแรงกับ kcal
- ถ้ามีรูป รูปต้องตรงเมนู
- ถ้าเป็นเมนูจาก AI ควรตรวจด้วยแหล่งข้อมูลอื่นก่อน

### 5.2 ปฏิเสธอาหาร

1. เลือกรายการที่ไม่เหมาะสมหรือข้อมูลไม่พอ
2. กดปฏิเสธ
3. ยืนยันการปฏิเสธ

ควรปฏิเสธเมื่อ:

- ชื่ออาหารไม่ชัดเจน
- ข้อมูลซ้ำกับรายการที่มีอยู่แล้ว
- ค่าโภชนาการผิดชัดเจน
- เป็นข้อมูล spam หรือไม่เกี่ยวกับอาหาร

หลังปฏิเสธ:

- รายการจะไม่เข้าสู่ catalog หลัก
- ถ้าผู้ใช้ถาม ให้แจ้งเหตุผลเชิงคุณภาพ เช่น ข้อมูลไม่พอ/ซ้ำ/ไม่ใช่อาหาร
- ถ้าเป็นเมนูที่มีประโยชน์แต่ข้อมูลไม่ครบ แอดมินสามารถเพิ่มเองใน `Foods` ได้

## 6. ตรวจชื่ออาหารท้องถิ่น

เข้าเมนู `Regional Names`

ใช้ตรวจคำเสนอชื่ออาหารท้องถิ่น เช่น ชื่ออาหารภาคเหนือ อีสาน กลาง ใต้

สถานะที่พบ:

- `pending`: รอตรวจ
- `approved`: อนุมัติแล้ว
- `rejected`: ปฏิเสธแล้ว

ขั้นตอนอนุมัติ:

1. เลือกรายการสถานะ pending
2. ตรวจชื่อภาษาไทยและภาค
3. เลือกว่าเป็นชื่อหลักหรือชื่อรอง
4. ใส่ popularity ถ้ามีข้อมูล
5. กดอนุมัติ

แนวทางเลือก `primary`:

- ใช้ `primary` กับชื่อที่ผู้ใช้ภูมิภาคนั้นน่าจะคุ้นที่สุด
- ถ้ามีชื่อหลักเดิมอยู่แล้ว การอนุมัติ primary ใหม่อาจทำให้ชื่อเดิมไม่เป็น primary
- ถ้าเป็นชื่อทางเลือก ให้ปิด primary และใช้ popularity แทน

แนวทางตั้ง popularity:

- `1`: ใช้น้อยมากหรือเฉพาะพื้นที่
- `3`: พบได้ทั่วไป
- `5`: เป็นชื่อที่นิยมมากในภูมิภาคนั้น

ขั้นตอนปฏิเสธ:

1. เลือกรายการที่ไม่ถูกต้อง
2. กดปฏิเสธ
3. ยืนยัน

## 7. ดูผู้ใช้

เข้าเมนู `Users`

สิ่งที่ทำได้:

- ดูรายการผู้ใช้
- ค้นหาผู้ใช้
- ดูรายละเอียดผู้ใช้ที่เลือก

ใช้เพื่อ support ผู้ใช้ เช่น ตรวจว่า user สมัครสำเร็จหรือไม่ อีเมลถูกต้องหรือไม่ และ role เป็นอะไร

ข้อมูลที่แสดง:

- User ID
- ชื่อผู้ใช้
- อีเมล
- Role
- Current streak
- Total login days
- วันที่สมัคร
- วันที่ login ล่าสุด ถ้ามี

ข้อควรระวังด้าน privacy:

- ใช้ข้อมูลผู้ใช้เท่าที่จำเป็นต่อการ support
- ไม่ export รายชื่อผู้ใช้โดยไม่จำเป็น
- ไม่ส่งข้อมูลอีเมล/พฤติกรรมการกินออกนอกทีม

## 8. เพิ่มหรือปรับสิทธิ์ Admin

ทำผ่าน Supabase SQL Editor หรือ database client เท่านั้น

ตัวอย่าง:

```sql
UPDATE users
SET role_id = 1
WHERE LOWER(email) = LOWER('admin@example.com');
```

ตรวจสอบ:

```sql
SELECT user_id, email, username, role_id, is_email_verified
FROM users
WHERE LOWER(email) = LOWER('admin@example.com');
```

ก่อนปรับเป็น admin ให้ตรวจ:

- บุคคลนั้นเป็นสมาชิกทีมจริง
- ใช้อีเมลที่ควบคุมได้
- บัญชีได้รับการยืนยันอีเมลแล้ว
- เข้าใจนโยบายข้อมูลผู้ใช้

การลดสิทธิ์:

```sql
UPDATE users
SET role_id = 2
WHERE LOWER(email) = LOWER('admin@example.com');
```

หลังลดสิทธิ์ ให้ผู้ใช้ออกจากระบบและ login ใหม่

## 9. Workflow ตรวจหลัง deploy

หลัง deploy Admin Web หรือ Backend:

1. เปิด `https://admin.caloriesguard.com`
2. Login ด้วยบัญชี admin
3. เข้า Dashboard ได้
4. เข้า Foods และค้นหาอาหารได้
5. เปิด modal เพิ่ม/แก้ไขอาหารได้
6. เข้า Food Requests ได้
7. เข้า Regional Names ได้
8. เข้า Users ได้
9. refresh URL ลึก เช่น `/users` แล้วไม่ 404
10. logout/login ใหม่ได้

## 10. API ที่ Admin Web ใช้งาน

| งาน | Endpoint |
|---|---|
| Login | `POST /login` |
| รายการอาหาร | `GET /foods` |
| เพิ่มอาหาร | `POST /foods` |
| แก้ไขอาหาร | `PUT /foods/{id}` |
| ลบอาหาร | `DELETE /foods/{id}` |
| Temp Foods | `GET /admin/temp-foods` |
| อนุมัติ Temp Food | `POST /admin/temp-foods/{tf_id}/approve` |
| ปฏิเสธ Temp Food | `DELETE /admin/temp-foods/{tf_id}` |
| Similar Foods | `GET /admin/foods/similar` |
| Regional Names | `GET /admin/regional-name-submissions` |
| อนุมัติ Regional Name | `POST /admin/regional-name-submissions/{id}/approve` |
| ปฏิเสธ Regional Name | `POST /admin/regional-name-submissions/{id}/reject` |
| Users | `GET /admin/users` |

## 11. Troubleshooting

| อาการ | สาเหตุที่เป็นไปได้ | วิธีแก้ |
|---|---|---|
| Login ไม่ได้ | อีเมล/รหัสผ่านผิด หรืออีเมลยังไม่ verify | ให้ user verify email หรือ reset password |
| Login แล้วกลับหน้า login | `role_id` ไม่ใช่ 1 หรือ token หมดอายุ | ปรับ role หรือ login ใหม่ |
| API 401 | token หมดอายุ | logout/login ใหม่ |
| API 403 | ไม่ใช่ admin | ตรวจ `role_id` |
| Upload รูปไม่สำเร็จ | backend/storage config ผิด | ตรวจ Supabase Storage และ backend env |
| Refresh `/users` แล้ว 404 | Cloudflare SPA fallback ไม่ทำงาน | ตรวจ `not_found_handling = "single-page-application"` |
